1 卡死解决方案（按成因 → 对策 → 工作包）

A 一次作答的同步链过长、随历史增长
  对策 A1：一次“继续/评分”动作建立一个读取上下文（沿用 StudyPathService.read_operation 范式），
    链内共享 current/counts/exposure_times/independent_ready_ids/content_rows/ability_teaching.state_map，
    提交前只重验最新状态；目标为一次作答只跑一次 current、一次 prepare_next_question、一次 reconcile。
  对策 A2：题目组装与入队候选在独立连接的后台线程计算（沿用 build_in_background＋页面令牌/修订校验），
    主线程只做最终校验与提交。
  对策 A3：主线会话前缀归档（沿用 practice_archive 轮次归档事务），整会话 json.dumps/sha256/扫描回到
    O(未完成题)。
  对策 A4：choose_protected 的 since=datetime.min 改有界窗口；resume_practice 用 lazy_questions；
    show_question 不二次 reconcile；is_content_available/get_setting 在一次动作内缓存解码结果。
  → WP3（A1、A4）、WP5（A2）、WP6（A3）。

B SQLite 写锁 busy 等待 10 秒 > ANR 5 秒
  对策：主连接 timeout 降至 2.5 秒；UI 写入口捕获 OperationalError(database is locked) 返回“稍后重试”
    状态而不整页阻塞；feedback.sqlite3 开 WAL；后台连接的 schema 检查改只读探测、缺失才写；
    archive_current 不在持有 progress 写锁时拿 feedback 库锁。PRAGMA synchronous=NORMAL 待用户决定（Q1）。
  → WP1（timeout、WAL、错误提示）、WP5（后台连接 schema 探测与锁顺序）。

C GIL 争用（启动预热与练习组装的 CPU 线程）
  对策：_reviewed_index 改为单飞（一个线程计算，其他调用者等待同一结果，主线程通过 await 等待而不重算）；
    review_data 与指纹索引改为构建期预计算（内容包携带），运行时只查表；后台 CPU 任务分片让出 GIL。
  → WP1（单飞）、WP6（预计算索引）。

D TTS 每条朗读同步绑定调用
  对策：音色选择结果按语言缓存（引擎重建/语言变化/音色列表变化时失效）；每条朗读只 speak；
    prepare_tts 的 getVoices 移出首帧路径。
  → WP1。

E 内存与 GC
  对策：启动导入完成后 gc.freeze()；_read_namespace 不长期持有解码原件（或只读视图代替 deepcopy）；
    varied_practice/context_choice 按 item_fingerprint 分片懒加载；validate_installed_pack 改文件级 sha256；
    运行时 load_namespace 调用点改模块级一次读取。
  → WP1（gc.freeze、运行时 load_namespace 调用点）、WP6（分片懒加载、文件级校验）。

F 原生回调里的裸 call_later 不唤醒
  对策：统一经 loop.call_soon_threadsafe 包装再 call_later（现有 app.py 2590 的做法推广到 1245/3362、
    learning_ui 231，及两处 create_task）。
  → WP1。

G 每键同步写盘
  对策：按键只改内存草稿，150–300 ms 防抖合并落盘；离页、提交、切后台、页面销毁时强制落盘；
    save_draft 返回轻量结果，fingerprint 在题目对象缓存一次。草稿语义不变：任何可见输入最终都落盘。
  → WP1（课程文本输入与假名练习 _checkpoint 的防抖）；最大延迟见 Q2。

2 题型模块化（插件化）

2.1 现状
题型相关逻辑分散在约 40 个模块：learning_questions（kind 常量表 KIND_ABILITIES/KIND_LABELS/DEFAULT_KINDS/
OPT_IN_LISTENING_KINDS/TEXT_KINDS/PRACTICE_ONLY_KINDS/KINDS_ADDED_AT、_word_question/_grammar_question 的
按 kind 分支、grade_learning_answer）、question_presentation（提示与 span 投影）、answer_input（输入资格）、
assessment_contract/assessment_parts（评分合同）、question_support（注音/TTS 安全门）、learning_ui 与各
*_ui（multi_cloze_ui、pitch_practice_ui、order_translation_ui 等）、practice_preferences（设置页）、
ai_question_capabilities（AI 可见能力）、word_sound_questions（两种读音题的模板生成）、learning_questions 内
context_choice 模板来源。新增一个题型要改十余处，且没有一处能回答“这个 kind 的全部行为是什么”。

2.2 目标形态
- 一个纯规则注册表 question_kind_registry.py：QuestionKindSpec（冻结数据类）字段：
    kind、label、family（word/grammar/pronunciation）、ability、default_enabled、opt_in_listening、
    needs_audio、text_input（自由输入）、practice_only（不进记忆检查/材料预测试）、added_at_version、
    template_source（"authored"｜"sound"｜"context_choice"｜…：模板来自哪个内容命名空间/生成器）、
    builder（从教案/模板构造题目快照）、grader（评分合同部件）、presenter（提示/span/折叠投影）、
    input_mode_policy（输入资格）、feedback_renderer_id、ai_capability（模型可见操作说明）、
    experimental。
  注册表只持有规格与可调用钩子，不持有内容、不读数据库、不依赖 Toga。
- 内置题型分文件实现：question_kinds/ 包，一个 kind 族一个模块（vocab_choice、vocab_text、vocab_sound、
  vocab_context、grammar_meaning、grammar_cloze、grammar_production、pronunciation）；每个模块只做
  build/grade/present/input 的 kind 专属部分，共享安全门与支架仍走 question_support/答题协调层。
- 现有消费者改为查注册表：KIND_ABILITIES 等常量从注册表派生并保留原名与原值（强约束：派生值与现值
  逐项相等，由冻结快照测试守住）；practice_preferences 的题型列表、标签、默认/版本补齐；
  ai_question_capabilities 的能力目录；course_planning/learning_practice_policy 只按 spec.ability 与
  spec.practice_only 过滤。
- “插件”的边界：插件是 App 内的代码模块（公开源码的一部分），不是内容包里的代码（内容包永不含可执行物）。
  内容库（08）只能为已注册 kind 提供模板；注册表提供 validate_templates(kind, payload)，未知 kind 的模板
  被忽略并记诊断，使旧 App 装新库时优雅降级。
- 迁移方式为“绞杀”（strangler）：先建注册表并让规格钩子委托给现有函数（行为零变化），再逐族把
  learning_questions/question_presentation/answer_input/assessment 中的 kind 分支搬进对应模块，每搬一族
  用题目快照黄金对照（全目录每 kind 每 variant 的 build_learning_question 输出哈希）证明逐字节不变；
  评分合同用现有 assessment 测试与 grade_learning_answer 对照。

2.3 不变项
kind 字符串、快照字段、评分结果字段、draft 结构、KINDS_ADDED_AT 的版本号、设置键 practice_queue_kinds 的
值域、PRACTICE_ONLY_KINDS 的排除语义、音频就绪扣除规则（audio_ready_kinds）、题型关闭的草稿合同（03 第 6 节）。

3 与可导入学习库（08）的衔接
- 库的 teaching 命名空间中的模板按 kind 登记；注册表是“kind 是否存在、模板结构是否合法”的唯一判据。
- 库清单可声明 requires.kinds（本库模板依赖的 kind 列表）；缺失 kind 的模板在合并时忽略并在内容库页提示。
- 有效目录的合并策略（08 第 6.2 节）对 learning_questions/varied_practice/context_choice/word_sound_mix
  命名空间按 kind→item_fingerprint 两级键合并；WP6 的分片懒加载与之共用分片键。
- 可用性投影（08 第 7–8 节）与题型注册表正交：前者决定内容项是否可派题，后者决定 kind 是否可出题。
