0 一句话方案

内容身份保持现状（不加包前缀、不改任何已有 ID），在内容层新增“库注册表＋有效目录”：
App 启动时按注册表合并所有已启用库的命名空间成一份只读有效目录；学习进度表不改结构、
不增列，所有“这项内容现在还在不在”的判断都由一个只读可用性投影在读取时得出；
不在有效目录中的已学项成为“孤儿项”，不再被任何派题、计数、入学、前置自动补齐和
调度查询选中，但其全部记录、到期与草稿原样保留，库再次启用即恢复。依赖以包内
depends_on 为主、包清单的跨包引用声明为辅，缺失依赖只阻止“新入学”，不阻止已学项复习。

1 现状盘点（事实，含代码定位） [I]

1.1 内容载体与加载方式
- 词典与假名：resources/content.sqlite3，只读，入口 content.py::ContentRepository。
  kana 表 165 行，id 形如 kana-3041；word 表 3130 行，id 形如 jmdict:1001820；
  metadata.content_version 当前为 enriched-material267-…。假名正式卡与词拼写记录的
  content_id 直接等于这里的 kana/word 行 id。
- 教学内容：resources/teaching_content.sqlite3，入口 content_pack.py。单文件、单 profile
  （personal/demo）、metadata 内含 namespaces 清单与整体 content_sha256，单命名空间上限
  64 MiB（2026-11-08 起，与库包 MAX_TEACHING_BYTES 一致），PERSONAL_REQUIRED_NAMESPACES 规定 personal 包必须齐全的 27 个命名空间。
  pack_path() 只认一个文件（环境变量 KANAMEMORY_TEACHING_PACK 或默认资源路径）。
- 附属只读资源：sentence_annotations.sqlite3、natural_translations.sqlite3、
  order_translations.sqlite3、lexical_sentence_review.sqlite3、learning_material_review.json
  （material_review.py 的已审修订覆盖层）、media/、glyph_origins/、NOTICE.txt。
- 加载时机：load_namespace 在 32 个模块的导入期被调用并写入模块级常量
  （如 learning_content._ITEMS、study_path_catalog.STAGES、course_prerequisites.FORM_CONSUMERS、
  learning_questions._CONTENT/_PRACTICE/_SOUND_MIX/_CONTEXT_CHOICE）。
  这意味着现行进程内容是进程生命周期常量；_read_namespace 的 lru_cache 以文件 mtime/size
  为键，只对“整文件替换后重启”有效。任何“不重启就切换库”的设计都先要解决这一点。
- 目录装配：learning_content._extend_catalogue 把 learning_content、三套语法课程、
  vocabulary_catalog、pronunciation_curriculum 合并进 _ITEMS，重复 ID 直接抛错；
  再由 course_prerequisites.apply_course_prerequisites 叠加审定前置并要求所有被声明的
  消费者都在目录中（缺一个就抛错）；最后 learning_dependencies.validate_catalog 拒绝缺失与环。
- 打包与分发：tools/build_teaching_content.py 从目录内 namespace JSON 生成教学包；
  tools/package_content_bundle.py 产出 kanamemory-content-bundle v1 ZIP（逐文件 sha256、
  禁止可执行后缀与学习者表、manifest 声明不含代码与学习状态）。04 第六节已明确：
  手机端热安装、自动升级、签名信任与云同步 UI 均为 P/U，不存在。

1.2 内容 ID 的形态与稳定性
- 课程项 ID 没有来源/包前缀，由作者约定保证全局唯一：
  word:jmdict:<entry>:<reading>:<sense_id>（词汇课 349 项）、
  word:<romaji>:<gloss>（基础 4 项，另有 WORD_IDENTITY_ALIASES 把词典身份映射到旧身份）、
  word:<word_id>:<reading>:<sense_id>（learning_item_from_word 为词典义项即时生成，dictionary_only）、
  grammar:<topic>:<key>（225＋exam 60＋usage 35）、pronunciation:<key>（45）、
  local:ai:…（AI/个人材料）。
- revision 与 item_fingerprint（material_review.py，ITEM_FIELDS）是“同 ID 内容是否变了”的
  判据；learning_questions 的已审模板、retired 变体、context_choice 模板都按 item_fingerprint
  绑定，ability_teaching.append 与 learning_dependencies.effective_dependencies 都要求
  保存快照与当前目录精确一致才叠加新信息。
- 学习路线把假名记为 kana:<id>:<script>，小节 ID 是阶段/单元/主题/深度的摘要
  （study_path_catalog.build_study_path）；study_path_v1 设置保存 added_sections 与
  reserved_entries 的字符串 ID。
- VOCABULARY_WEAVE、SEMANTIC_GROUPS 等按词形字符串而非 ID 关联；这类“按表面形式”的
  关联在多库合并时最容易误连，第 6 节单列。

  explicit_learning_start_v1、study_path_v1、kana_introductions_v1、kana_ability_bridges_v1、

  _unavailable_content_ids 是现成的“读时过滤集合”范式。

  LearningStore.content_question_blocked 统一入口，counts 计入 blocked_material，
  current 返回 content_blocked 状态。

- example_store 对消失的 target 标 unavailable、保留身份、不按标题重连。
- effective_dependencies 的签名比较：保存快照与当前目录不一致时不叠加前置，

2 目标与非目标

目标
G1 用户可添加、移除、启用、停用多个学习库；每个库有清晰的身份、版本、来源与校验。
G2 现有全部课程内容可以不改任何 ID 地整理为一个库（“核心库”），现有用户零迁移。
G3 同一内容在多库出现、或同 ID 不一致时有确定的解析结果与可见的冲突提示。
G4 库移除/停用后，其内容不再进入任何学习过程与调度，但进度不丢；再次启用即恢复。
G5 更大的库带来的未学依赖能被识别、按既有引入路径排队，不自动授予掌握。
G6 依赖建模覆盖包内声明、跨包引用、循环、缺失与版本升级。
G7 与 FSRS 参数、辅助证据权重、记录格式不变的约束兼容；备份/恢复校验不依赖目录。

非目标
N1 不做云同步、商店、自动更新与远程签名基础设施；首版签名只做“记录与可选校验”。
N2 不做进程内热切换库；首版库变更后“重启生效”（见 11 风险 R1）。
N3 不合并两条不同 ID 的进度记录；别名只影响新入学与显示，不迁移历史。
N4 不把词典（content.sqlite3）拆成多库；首版词典是核心库的一个不可移除分层。
N5 不改变任何题型、评分、曝光、辅助证据、题型开关与返回语义。
N6 不为移除的库删除学习记录；删除学习数据仍只走现有 learning_reset 与用户显式操作。

3 术语与总体模型

- 库（library）：用户可见的安装单元，有 library_id、标题与来源；同一 library_id 在设备上
  至多一个已安装版本。
- 包（pack）：库的一个版本文件（ZIP），格式见第 4 节。安装＝校验＋复制到应用私有目录
  ＋写注册表；移除＝写注册表＋可选删除文件。
- 分层（layer）：包内按用途分的文件组：teaching（命名空间 JSON 或教学 sqlite）、lexicon
  （词典/假名 sqlite，首版仅核心库）、annotations（句注/译文 sqlite）、media、review
  （learning_material_review 类覆盖层）、notice。
- 命名空间（namespace）：沿用 kanamemory-teaching-namespace v1 文档；新增“合并策略”元信息。
- 有效目录（effective catalogue）：按注册表启用顺序合并全部库后得到的只读内容视图，
  对消费者而言与今天单包的 load_namespace 结果同形。
- 可用性投影（availability view）：一次读取动作内计算的 {content_id → available|orphaned|
  blocked_dependency|retired} 映射，由 Store 提供、页面只读，不持久化。
- 孤儿项（orphan）：已有进度记录但不在有效目录（或所属库已停用）的内容项。

数据流
  安装包文件 ─校验─> 库目录（应用私有） ─注册表 content_libraries_v1─> 启动时合并
  ─> 有效目录（只读，进程常量） ─> load_namespace 同形接口 ─> 现有消费者
  进度库（不变） ─ 读取时 ─> 可用性投影 ─> 派题/计数/入学/路线/首页 过滤

4 包格式

4.1 文件布局（ZIP，不含任何可执行后缀，沿用 package_content_bundle 的拒绝规则）
  manifest.json
  teaching/<namespace>.json      —— kanamemory-teaching-namespace v1 文档，一个命名空间一文件
  lexicon/content.sqlite3        —— 仅核心库；第三方包不得携带（首版）
  annotations/*.sqlite3          —— 可选
  media/…                        —— 可选
  review/learning_material_review.json —— 可选
  NOTICE.txt                     —— 必需
  signature.json                 —— 可选，见 4.5

4.2 manifest.json 字段
  format: "kanamemory-library-pack", version: 1
  library_id: ^[a-z][a-z0-9_.-]{2,63}$（如 kanamemory.core、kanamemory.demo、author.n3_grammar）
  library_version: 字符串，排序规则显式声明为 "date"（YYYYMMDD[.n]）或 "semver"
  title / description / language_pair（如 ja-zh）/ authors / license（SPDX 或自由文本）/ license_notice
  requires: { app_min_version, teaching_format: 1, namespace_version: 1 }
    app_min_version（可选）：能用这个库的最早应用版本，点分数字（0.36 或 0.36.0）。导入时与应用自己的版本逐段比较，应用较旧就
    拒绝并说明需要哪个版本（I，2026-11-14；0.35.0 及更早的应用只保存这个字段、不比较）。不是点分数字的旧写法无法比较，不据此
    拒绝；打包工具只写可比较的值（--app-min-version）。
  profile: "core" | "extension"；core 必须满足 PERSONAL_REQUIRED_NAMESPACES（demo 另有 demo 子型），
    extension 可以只带部分命名空间
  layers: 各分层相对路径列表
  files: { 相对路径: { bytes, sha256 } }（manifest 自身不含在内）
  content_sha256: 对 files 按路径排序后的 (path, sha256) 列表取 sha256
  provides: { items: [content_id…], namespaces: [name…] }
  references: [ { id, kind: "item", requirement: "required"|"optional", note } ]
     —— 本包 depends_on/背景/路线里引用但本包不定义的内容 ID（跨包引用声明，第 9 节）
  depends_libraries: [ { library_id, version_range } ]   —— 包级依赖（可为空）
  overrides: [ { id, reason } ]  —— 有意替代其他库同 ID 内容的明确声明（第 6 节）
  retires: [ { id, replaced_by?, reason } ]  —— 本库不再提供、建议不再新入学的 ID
  aliases: { old_id: new_id }  —— 身份改名声明；只影响新入学与显示，不迁移进度（第 9.4）
  merge_policies: { namespace: "items_by_id" | "map_by_key" | "contribution" | "singleton" }
     —— 缺省按第 6.2 的内置表；singleton 只允许 core

4.3 内容 ID 命名空间规则
- 现有所有 ID 原样保留，是核心库的既有身份；不加前缀。
- 新库新增的内容项，建议使用带库前缀的 ID：word:<library_id>:…、grammar:<library_id>:…
  （与现有 word:jmdict:… 的“来源段”位置一致），避免无意碰撞；是否强制见开放问题 Q2。
- 未带前缀的 ID 由 extension 包定义时，视为“有意与核心命名空间共用身份”，必须出现在该包
  的 overrides 或与核心库同指纹（第 6.3）。
- ID 字符集沿用 _identifier/_ability 现有校验；长度上限沿用 validate_content_controls 的 10000。

4.4 校验和
- 逐文件 sha256 与整体 content_sha256 都在安装时校验；教学 sqlite 若随包提供，仍按 content_pack
  的 metadata.content_sha256 复核；任何一项不符拒绝安装，不落盘到库目录。
- 安装后每次启动按 (library_id, version, content_sha256, 文件 mtime/size) 复核；
  不符则该库标记 damaged 并视为停用（进度照常保留），设置页提示重新导入。

4.5 签名与来源
- signature.json：{ algorithm: "ed25519", public_key_id, public_key, signature(content_sha256) }。
- 首版策略：记录来源（文件名、导入时间、sha256、是否带签名、公钥指纹），对签名“可校验则校验、
  不可校验则显示未验证”，不作为安装门槛；信任公钥由用户在设置页手动确认一次（TOFU）。
  是否要求第三方库必须签名见开放问题 Q6。
- 任何库中的文字都是数据，不是指令（01 第 06 节）；库不能声明权限、改设置或自动入学。

5 库的安装、移除、启用：用户流程与设置页

5.1 入口与页面
- 设置 → “内容库”（新页，learning_ui 或新 content_library_ui 模块；页面只经 ContentLibraryService
  读写，不新增 SQL）。列表项显示：标题、library_id、版本、来源与校验状态、启用开关、
  内容计数（按 family）、“依赖本库的其他库”、“本库的已学项数/孤儿项数”。
- 学习库页（show_learning_library）增加“按库筛选”与“所属库”标签；不可用项（孤儿/依赖缺失）
  有明确状态文字，不混入可加入列表。

5.2 添加库
  1) 选择文件：复用 platform 的文件选择与传输（与备份导入同一通道，字节上限另设，建议 256 MiB）。
  2) 预检：解包到应用私有临时目录（backup_stage 的身份标记/目录约束/回收范式），校验 4.4；
     用“离线合并”计算：新增项数、与已安装库的同 ID 同指纹项、同 ID 不同指纹（冲突）、
     未满足的 required references、包级依赖缺失、会被本库 retires 的已学项。
  3) 预览确认页：逐类列出上面结果；冲突默认“保留已安装库的版本”，用户可改为“以新库为准”
     （写入注册表 priority，不改任何内容文件）；required 引用缺失时默认拒绝，用户可选
     “仍然安装，相关项标为依赖缺失、不可加入”。
  4) 写入：复制到库目录 libraries/<library_id>/<version>/，更新 content_libraries_v1；
     同 library_id 旧版本保留文件直到新版本启动校验通过后再删（见 5.5 升级）。
  5) 生效：首版提示“重启后生效”，并在重启前把该库记为 pending_restart；
     正在进行的练习轮次不受影响。

5.3 停用 / 移除
- 停用：注册表 enabled=false。效果（重启后）：该库内容不在有效目录；其已学项变孤儿（第 7 节）；
  依赖它的其他库中的项变 blocked_dependency。进度不变。
- 移除：停用 ＋ 删除库目录文件。确认页必须显示“已学项 N 个将变为孤儿，进度保留；再次导入
  相同 library_id 即恢复”。核心库不可移除（首版）。
- 两者都要求当前没有未结束的独占阶段（备份/恢复进行中）且不在练习轮次中间；
  复用 backup_ui 的独占阶段与页面令牌模式。

5.4 启用顺序 / 优先级
- 注册表保存显式 priority 列表（越靠前越优先）；默认核心库最低优先级还是最高，见 Q3。
  本文建议：核心库最高优先级，第三方库只能通过 overrides 显式替代核心项。

5.5 升级同一库
- 新版本包安装走 5.2；预览额外显示：指纹变化项数（已学项中有多少会出现“保存快照与目录
  不一致”）、被 retires 的项、aliases；安装成功后旧版本目录删除。
  更新不改变启用开关（2026-11-12，一轮原生实测后修正）：原先安装新版本会把已停用的库重新启用；现在保持原状态，
  预览页写明“更新后仍保持停用”，安装结果提示同样说明。升级差异读的是已安装版本的清单文件，与该库是否启用无关。
  库目录的符号链接检查只针对库根目录以下、库自己的文件夹：安卓上应用数据目录经由系统链接 /data/user/0 到达，
  原先检查所有上级目录，使服务层在设备上读不到任何已安装清单（升级差异按空库比较、库行“已学 0 项”、移除提示计数为 0、
  预检缺少其他库的指纹）；电脑上不出现。内置核心库一行的数量只计“没有任何扩展库提供”的项（原先把已载入扩展库的项也算入）。
  预检结果里的“新增内容／相同／冲突”只与继续保留的库比较，不与被替换的旧版本比较：原先用进程里已载入的目录代表“已安装内容”，
  旧版本已载入时新包与自己的旧版本“冲突”并给出未声明 overrides 的提示（0.34.0 审计 U1），旧版本停用时又把全部项算成新增
  （一轮原生实测：新增 1388 项）。现在由本库旧版本提供的项从已安装指纹与目录中剔除（同 ID 的核心项仍算冲突），
  precheck_pack 新增 previous_ids：旧版本已有的项既不算新增也不算相同，“新增内容”即本次更新真正新增的项，启用与否结果相同。
  规则 c 对被替换的版本单独核对（内容变了而修订号未变即包错误），不再依赖旧版本是否已载入。
- 已学项的升级语义沿用现行合同：保存快照为准；只有未动过且精确匹配旧指纹的项才接受新前置叠加；
  有真实作答/草稿/冻结结果的项保留原路线（effective_dependencies/preserves_existing_route）。
  版本变化不会重写 content_json、题面、草稿或到期。

5.6 注册表 content_libraries_v1（app_setting，一条 JSON）
  { version: 1,
    libraries: [ { library_id, library_version, profile, content_sha256, enabled: bool,
                   installed_at_utc, source: {kind: bundled|file, name, sha256, signature_status},
                   path (相对应用私有目录), state: ready|pending_restart|damaged } ],
    priority: [library_id…], trusted_keys: [ {public_key_id, public_key, confirmed_at_utc} ] }
  校验函数放纯规则模块（content_library_rules.py）；写入归 StudyStore.set_setting 的现有事务；
  备份：建议导出时携带（供恢复后提示“你原来装了哪些库”），恢复时不据此安装文件、不据此改
  当前注册表（设备配置属于本机），见 Q7。learning_reset 不删除注册表。

6 内容解析：多库合并、冲突规则与优先级

6.1 有效目录的构造（启动时一次，失败即回退）
  1) 读注册表，按 priority 取 enabled 且校验通过的库。
  2) 逐命名空间按 merge_policies 合并（6.2）。
  3) 执行现有目录装配链：_extend_catalogue 的重复 ID 检查改为“冲突解析后仍重复才报错”；
     apply_course_prerequisites 对 extension 库贡献的规则，消费者缺失时按“该库的规则不生效并记录”
     处理，而不是整体抛错（核心库规则仍严格）；validate_catalog 仍拒绝环。
  4) 任一步失败：记录诊断（diagnostic_events 允许字段），回退到“仅核心库”有效目录并把
     出错库标记 damaged（停用语义），保证 App 仍能启动且进度可读。
  5) 结果与一份 catalogue_token（库 id/版本/sha 的摘要）一起作为进程常量；
     备份恢复后不需要重建（内容与进度分离）。

6.2 命名空间合并策略（内置表，manifest 可声明但不得放宽）
  items_by_id（按 id 合并，冲突走 6.3）：learning_content._WORDS/_GRAMMAR、grammar_curriculum._ITEMS、
    exam/usage/pronunciation 的 _ITEMS、vocabulary_catalog.WORD_LESSONS、example_catalogue、
    example_expansion_*、structured_lessons_*、lesson_diagrams_*、learning_questions（按 item_fingerprint
    键的模板表与 GRAMMAR_QUESTIONS）、varied_practice、context_choice、word_sound_mix、question_contexts、
    reading_annotations、semantic_assessments、pitch_sequences。
  map_by_key（键唯一，冲突走 6.3）：presentation_metadata、foundation_content、
    sentence_annotation_overrides、vocabulary_lessons 的 SENSE_INDEXES/WORD_BINDINGS/WORD_IDENTITY_ALIASES。
  contribution（追加贡献，不覆盖）：course_prerequisites 的 SEMANTIC_REQUIREMENTS/FORM_CONSUMERS
    （规则按库记录来源，只对有效目录中存在的消费者生效）、study_path_catalog 的 WORD_TOPICS、
    GRAMMAR_TOPICS、UNIT_CONTEXT_TITLES、VOCABULARY_WEAVE、SMALL_UNIT_PLANS（新库的内容进入
    “扩展”阶段或由库声明所属阶段）、SOURCES/SOURCE_RECORDS（来源记录并集）。
  singleton（只允许核心库提供）：STAGES、PATH_VERSION、COHERENCE_RULES、GRAMMAR_ROUTE_CONFIG、（这些只描述核心主线；平行学习路线提案 10 拟新增命名空间 study_routes，items_by_id，键 route_id 须以库 id 为前缀）
    PRONUNCIATION_ROUTE_CONFIG、course_prerequisites 的 FORM_BASES/TE_FORMS 等形态基底表、
    CONTENT_REVISION/VOCABULARY_REVISION 等修订号（extension 库的修订号进入其 provenance）。
  按“表面形式”关联的表（VOCABULARY_WEAVE.word_forms、SEMANTIC_GROUPS）：合并后只在同一库内
  解析词形到 ID；跨库同词形不自动关联，预检列为提示。
  loanword_origins（外来词来源，设计 11 第 19 节，2026-11-14）不在内置表里：它的 items 按默认规则 items_by_id 合并，同 id
  冲突时核心优先并照常报告。扩展库只为自己的词课写条目；写给别的库词课的条目，在该库自己的包检查里报“没有对应词课”。

6.3 同 ID 冲突规则
  a) 同 ID 且 item_fingerprint 相同：视为同一内容，provenance 记录多个来源，无冲突。
  b) 同 ID 不同指纹：
     - 若较低优先级库在 overrides 中声明了该 ID，且用户在预览中接受，则以该库为准（priority 提升
       仅对该 ID 生效，记录在注册表 overrides_accepted）；
     - 否则以 priority 更高的库为准，冲突写入“内容库”页的冲突列表（可查看两边标题/读音/释义差异）。
  c) 同 ID 的 revision 必须随指纹变化；同 revision 不同指纹视为包错误，预检拒绝该包。
  d) 读音/释义不一致但 ID 不同（如 word:jmdict:…:がっこう 与 word:other:gakkou）：
     不是冲突，是“疑似重复”；预检按 (title, reading, 词典 sense sha) 匹配给出提示，
     由库作者通过 aliases 或 references 显式表达，App 不自动合并，也不合并进度（N3）。
  e) 已学项不受解析结果影响：learning_content.content_json 快照始终是该项的教案权威；
     解析只决定“新入学用哪份”“未动过的项能否叠加新前置/模板”。

6.4 模板、例句与覆盖层的归属
- 已审模板按 item_fingerprint 绑定，天然只服务与之匹配的教案；换库后指纹不匹配的已学项
  不再获得新模板，沿用保存快照与 legacy 行为（现行合同），本设计不改。
- learning_material_review.json 类覆盖层按库隔离：只对本库定义的项/题生效。
- 共享例句包（example_store）target 不在有效目录时沿用现有 unavailable 处理。

6.5 扩展库文档的按需读取 [I，0.34.2，2026-11-12；合成数据单元与集成测试、桌面实测；原生验证见 README]
问题（一轮原生实测，一个 1,388 项、6 个文档共约 70 MB JSON 的扩展库）：启用后每次启动把所有文档整份解码并再复制一份，
  桌面上教学内容占用 56 → 504 MB、载入 0.45 → 5.4 秒；模拟器 PSS 约 1 GB、到第一题 22 秒（核心库单独 335 MB、9.8 秒）。
  而一次学习只用到几课。核心包早已按分片逐条读取（content_pack 的 ShardedNamespace），扩展库没有对应机制。
包格式、manifest、注册表、学习记录和题目快照都不变；已安装的库无需重装。
- 索引（content_library_index，纯规则，pure_imports 登记）：把一个命名空间文档走一遍，得到“骨架”——与原 payload
  相同，只是两类大值换成对文档字节区间的引用 [offset, length, sha256]：
  1) 学习目录表（_WORDS/_GRAMMAR/_ITEMS/WORD_LESSONS，列表或按 id 的映射）每一行的 question_templates（它是 JSON 对象时）；
     行的其余小字段留在骨架里，目录、前置关系、列表都只靠骨架。
  2) items 表（question_dependencies、question_readings、varied_practice、context_choice 这类按内容 id 的记录）的每个条目。
  带类型标签的表、非对象的 payload 等不建索引（LibraryIndexError），调用方整份解码，行为与原来相同。
- 存放：库文件夹内 .index/<命名空间>.json，派生数据，随文件夹删除（包里的路径不允许以点开头，所以这个目录只属于 App）。
  索引写明文档的 sha256、字节数与文件修改时间并自带校验和；安装时写（ContentLibraryService.install，尽力而为）；
  启动时没有、读不了、或与文档不符（含修改时间不同：文件被重新写过），就整份校验读取文档后重建并写回；
  文件夹写不了也照常按需读取，只是下次启动再建一次。0.34.1 及以前安装的库在升级后的第一次启动时建索引
  （桌面 2.0 秒，其后每次 1.0 秒；原来每次 5.4 秒）。
- 接受与拒绝和整份解码一致：启动时建索引会把每个延迟部分过一遍 decode_value（骨架由 resolve 解码），任何一处不被
  接受就按原路整份解码并报原来的错；安装时刚做过整份解码的预检，建索引不重复这一步。
- 校验语义与核心包分片一致：有索引时启动只核对清单、文件大小（原有）、修改时间和索引本身；每个被引用的部分在第一次
  读到时按 sha256 核对。读不出或不符时（介质上的损坏、文件丢失）在读取处报 LibraryIndexError（ValueError；文件错误也
  转成它），同时记一条 content_library/read 诊断并删掉这个文档的索引：下一次启动没有索引，整份校验读取，校验和不符，
  该库像以前一样被判为损坏、本次只载入核心库。整份校验仍在三处：安装、建索引、损坏库的复检（read_namespace）。
  被本进程读着的旧版本文件夹不在本次启动清理（_remove_superseded 与 _delete_pending 同一条规则）。
- 索引可以存放 JSON 允许的不成对代理转义（surrogatepass），这样的文档不会因为建不了索引而被判为损坏。
- 运行时表示：行里的 question_templates 是 LazyMapping，items 表是 LazyTable，都是只读映射。
  deepcopy 得到普通的独立数据，所以 get_learning_item / learning_items / reviewed_item 的返回值与原来逐项相同；
  isolated_copy 是“保留延迟值的独立拷贝”，用于 load_namespace 的隔离拷贝和目录构建（learning_content._rows、
  study_path_records）。指纹（material_review.without_order_translations）把只读映射当作它代表的普通映射。
  读过的部分按来源字节数限量保留（2 MB），超出即淘汰，下次再读。
- 只读的目录接口：learning_content.learning_item_views(family) / learning_item_view(id)。每项是独立的 dict，
  与 learning_items 的快照相等，只是 question_templates 是目录自己的只读映射（扩展库的是延迟值）而不是拷贝；
  review 数据点名的项仍走 reviewed_item。约定：视图不得直接序列化（json 会报 TypeError）或改动模板，需要时先 deepcopy。
  已改用视图的调用点（都只读小字段，或在取用处 deepcopy）：可用性的前置表（content_library_service._catalogue_dependencies）、
  ensure_prerequisites 的目录（计划里要报名的项由 build_dependency_plan deepcopy）、读音题的词池（_word_pool）、
  例句条件索引（learning_conditions._reviewed_index 与 bundled_example_pack）、背景词义索引（question_support）、
  结构化讲解的原件表（structured_lessons.catalogue）、学习路线服务与路线构建（StudyPathService、study_path_records；
  报名时 original_source 会 deepcopy）、学习库列表页（learning_items_available(views=True)，行的处理函数交出 deepcopy）、
  例句服务（见下）、课程详情按 id 打开与前置计划／加入学习时的目录、“试做新内容”的候选扫描、例句关联的选择与导入预览、
  读音显示的课内写法表（question_readings._lesson_forms）。
  其余调用点仍取完整快照：每次为扩展库的每一项解码一次模板（比原来的 deepcopy 快，但仍与库的大小成正比）。
- 例句服务（原生实测定位）：启动时后台预建的 ExampleStore 用 learning_items_available() 取完整目录并
  把每一项 deepcopy 后保留到会话结束——设备上启用大库后多出的约 250 MB 就在这里（第一轮改动后 PSS 仍有 479–640 MB）。
  现在它取视图（example_targets_available(views=True)），自己保留的是 isolated_copy；bundled_catalogue 的“原件”
  用 original_source(isolated_copy(项), owned=True)，备忘键用 digest_default 序列化（视图与它代表的普通项得到同一段
  文本，延迟值以其字节的校验和入键、不读取）。生成的例句目录与原来逐字节相同。桌面：带库时这一步 408 → 230 MB
  （不带库 193 MB），3.8 秒（原 7.4 秒）。
- 同时去掉三处“给整个目录算指纹”，都是结果不变的改写：_reviewed_targets 与 reviewed_pack 只给 review 数据列有
  目标指纹的 id 算指纹（没列的 id 无论指纹是什么都不匹配）；effective_dependencies 先看内置前置是否有可加的项，
  有才比较教案指纹（没有可加的项时，匹配与否结果都是原前置）；bundled_example_pack 只对 review 数据点名的项调用
  example_source_item（其余项它只是原样拷贝）。
- 桌面实测（同一个扩展库的后一版，同一份学习记录）：教学内容占用 504 → 70 MB（不带库 53 MB），载入 5.4 → 0.9 秒（不带库 0.5 秒）；
  “继续学习”到第一题 14.5 → 5.3 秒（不带库 4.3 秒）；索引合计 2.9 MB，建索引时峰值多约 60 MB。
- 独立审计：真实库与 30 个手工 JSON 边界用例上按需读取与整份解码逐项一致，
  三处改写结果不变；提出的四点（不成对代理、损坏只在使用处暴露、测试夹具的缓存、索引版本号的说明）均已采纳，见上。
- 未做：仍取完整目录的调用点——AI 学习助手各页（example_targets_available 的默认形态、材料核对与学习）、例句编辑页、
  个人笔记关联、反馈影响分析、假名前置修复；这些页面打开时会为扩展库的每一项解码一次模板（一次性的内存高峰）。
  核心库自己的行内模板没有改成延迟（核心包的大表本来就分片）。

7 进度与内容分离：孤儿项状态机与恢复语义

7.1 原则
- 进度表零结构变化：不加列、不加表、不改 TABLES；可用性是读时投影，不落库。
- 唯一新增持久项是注册表 content_libraries_v1（第 5.6）。备份校验 validate_backup_rows 增加对
  该键形状的校验（与 intro_batch_state.validate_database 同范式），不校验库文件是否存在。

7.2 状态（读时计算，纯规则 content_availability(catalogue, registry, item_row)）
  available            内容在有效目录且其库启用；首版还要求目录指纹与快照一致或项已开始
                       （开始＝有事件/草稿/冻结结果），未开始且指纹不一致的项按现行
                       effective_dependencies 规则处理，不算孤儿
  orphaned             content_id 不在有效目录（库停用/移除/新版本 retires 且无 alias）
  blocked_dependency   在目录中，但某个 required 依赖不在目录且该依赖从未取得前置资格
  retired              库声明 retires 且 replaced_by 可用：显示为“已被 X 取代”，不再派新题
  说明：family=word 且 dictionary_only 的即时词典项，以词典分层（核心库）存在为准；
  local:ai:* 个人材料不属于任何库，始终 available（受其自身材料资格门控）。

7.3 转移
  available → orphaned：库停用/移除/升级移除该 ID。无写入；下次读取即生效（重启后）。
  orphaned → available：库重新启用/重新安装且提供同 ID。
     - 指纹相同：完全恢复，到期按实际经过时间由 FSRS 自然处理（与 03 第 7 节“长期停学不归零”
       一致），pending 题目按原快照可答，草稿原样。
     - 指纹不同：恢复为 available，但按 5.5 升级语义：已开始的项保留原快照与路线；
       未开始的项下次派题用新目录（effective_dependencies 现行规则）。
  orphaned 期间允许的操作：查看学习记录与历史、备份/恢复、删除学习数据（整体）、
     个人注释查看；不允许：入学、追加能力、派新题、评分、辅助证据写入、前置叠加。
  任何状态都不触发 learning_unit.suspended 写入：suspended 是用户意图，orphan 是内容事实，二者分离。

7.4 与现有机制的边界
- 不复用 study_item_controls_v1 表达孤儿（那是用户停用意图，且会随备份迁移）。
- 不生成 learning_replacement 回执（那要求有替代题）；孤儿的 pending 题保留 pending，
  只是不被派发（与关闭题型的课程草稿保留行为 d 类似，03 第 6 节）。
- 孤儿项在练习轮次中：轮次题单在冻结时按可用性过滤；库变更要求不在轮次中（5.3），
  因此不会出现冻结题单含孤儿的情况；若因 damaged 回退出现，practice_round 下一次 restart 自然排除。
- 恢复备份：备份里可能含本机没有的库的已学项，按 orphaned 显示，不拒绝恢复（G7）。

9 依赖关系的建模与处理

9.1 声明层次
  L1 项级 depends_on（现有）：同库或跨库的内容 ID 列表；是“首次教学先后”的硬前置。
  L2 规则贡献（现有 course_prerequisites 形态/语义规则）：核心库为 singleton 基底；extension 库
     只能以 contribution 方式追加 SEMANTIC_REQUIREMENTS/FORM_CONSUMERS 条目，且只对有效目录中
     存在的消费者生效。
  L3 题目背景 background_ids（现有）：出题门，不是入学门。
  L4 包级 references（新）：本包引用但不定义的 ID，requirement=required|optional。
     required 引用缺失 → 相关项 blocked_dependency；optional 缺失 → 仅去掉该条前置/背景。
  L5 包级 depends_libraries（新）：粗粒度提示与安装顺序建议；真正的闭包判断以 L1+L4 为准。
  安装预检对 L1 的每个跨包 ID 要求在 L4 中声明，否则列为包作者错误（警告级，可继续安装，
  运行时按 required 处理）。

9.2 校验点与失败语义
  安装预检（离线合并）：缺失 → 列表；环 → 拒绝该包（给出 path，validate_catalog 现有错误）；
  同库内缺失 → 拒绝（包不自洽）；跨库缺失 → 按 required/optional 处理（9.1）。
  启动合并：同上，但失败走 6.1 的回退，不阻止启动。
  运行时：build_dependency_plan 的 unresolved.reason 增加 "unavailable"（库停用）与
  "blocked_dependency"；prerequisite_status 的 _status 增加 state "unavailable"：
    - 该前置已有真实无辅助成功（在 independent_ready_ids 中）→ ready，不阻塞后继（历史资格不撤销）；
    - 否则 → 后继 blocked，原因显示“前置 X 所在的库已停用/缺失”，提供“去内容库”入口；
      用户仍可用现有“我已了解前置”自报（prerequisite_acknowledged）放行，自报不是成功证据（不变）。

9.3 大库带来的未学依赖：识别、排队与引入
  识别：添加页/学习库页对目标项显示闭包预览（build_dependency_plan 的 to_enroll 按 family 计数：
    假名 N、读音规则 N、语法 N、词汇 N），并标出其中“已在学”“已通过”“需新学”。
  排队：沿用 enroll_with_prerequisites 的前置先行顺序（validate_catalog 的稳定拓扑序）：
    - 假名/读音规则前置：进入假名专项/规则路线（ensure_kana_queue.with_prerequisites、kana_dependency_runtime）；
    - 词汇/语法前置：按四之二批引入（intro_batch_candidates 只取 stage=intro 项，批量沿用设置）；
    - 目标项本身入学为 intro，但 prerequisite_status 阻塞直到前置取得真实成功；
      调度公平由 first_teaching_dispatch/new_dispatch 现有规则处理，不新增配额。
  节奏（新增，纯规则 dependency_frontier）：一次“添加”动作最多自动入学 K 个新前置
    （建议 K＝词汇批量＋语法批量＋假名 5；用户可在确认页改为“全部加入”），其余前置保持
    “计划中、未入学”，由后续“继续学习”在前沿推进时再入学；避免一次添加几十项造成首学积压
    （03 第 7 节已有积压观察）。这不是每日新增上限，只是分批入学。
  “我已经会了”：沿用四之二说明卡的检验路径与 60 秒曝光门；假名沿用现有熟悉度三选；
    通过检验的前置按现行“已熟悉→实际检验”语义进入调度，不因是前置而放宽。
  大库移除：目标项不变，前置变孤儿：已通过的前置资格保留（independent_ready_ids 来自历史），
    未通过的 → 后继 blocked（9.2）。

9.4 版本升级与身份变化
  - 新增依赖：只对未动过、精确匹配指纹的已学项叠加（effective_dependencies 现行合同）。
  - 删除依赖：直接生效（放宽不伤害进度）。
  - 删除项：无 alias → orphaned；有 retires.replaced_by → retired，新入学指向替代项，旧进度保留。
  - 改名（aliases old→new）：有效目录对 old 的查询返回 new 的内容但 id 字段仍为 old（供已学项展示与
    模板指纹匹配）；新入学只用 new；两份进度若都存在不合并（N3），内容库页提示“同一内容两条记录”。
  - 包级依赖版本范围不满足：预检警告；运行时不据此停用，按 L1/L4 的实际缺失处理。

9.5 与 ability_teaching / new_dispatch / 四之二 的衔接
  - ability_teaching.append 的“教案版本与原记录不同”检查不变；孤儿项不调用它。
  - admit_word_listening 的候选扫描排除孤儿；恢复后自然继续，日限量不变。
  - new_dispatch 的 lane 轮转读 current 结果，无需改游标格式；孤儿项不会成为“已打开课程块”。
  - intro_batch：批状态中的 content_id 若在批进行中变为孤儿（只可能因 damaged 回退），
    complete_intro_batch 前检查并把该项从批中剔除为 pending（保留检查点），不评分、不清草稿。

  的运行合同对照（runtime_contract_*.json）方式再做一次“9874 观察一致”式的回归（0.24.0 做过）。

10.2 向后兼容

11 风险

R1 进程常量内容：32 个模块在导入期固化命名空间。首版“重启生效”可接受，但 App 必须在
   安装/停用后给出明确重启入口并拒绝在重启前继续派题；否则会出现“设置页显示已停用、
   队列仍在出该库的题”。长期可改为延迟读取（模块级 _CONTENT 改为属性访问），属 07 层工程债。
R2 模板按指纹绑定：换库/升级后未开始项的模板来源变化会改变新题，已开始项不受影响；
   需在升级预览中用数量告知用户，并在回归里固定“已开始项题面不变”。
R3 跨库“表面形式”关联（词形、语义组）误连或漏连：首版只在库内解析，预检提示。
R4 大库的前置闭包可能很大，首学积压与首页“待前置”数激增：dependency_frontier 分批入学，
   首页文案区分“计划中”与“已入学待前置”。
R5 启动合并失败的回退：若核心库自身损坏仍要能打开学习记录与备份页；这是 content_pack
   现有“先校验再开学习库”的反向要求，需要单独的只读安全模式页面。
R6 注册表随备份迁移会把 A 机的库列表带到 B 机：本文建议只携带不应用（Q7）。
R7 第三方库文字进入提示词/AI 请求：现行 04 的有限上下文边界不变，但库来源要在 Tutor
   上下文里显式带出处，避免把未审内容当“已审”。
R8 签名首版不强制：用户可能导入被篡改但哈希自洽的包；用 TOFU 公钥与来源显示降低风险，
   并在 Q6 征求是否强制。
R9 公开边界：库格式文档与工具公开，课程内容与作者工具仍私有；新模块须加入公开清单，
   测试须在 demo 导出树可跑（用 demo 库作为夹具）。

- app/src/kanamemory/content_library_signing.py（新，纯规则，pure_imports 登记，只用标准库）：RFC 8032 Ed25519 的纯 Python
  实现（public_key_from_seed/sign/verify；Android 运行时没有 cryptography/pynacl，签名工具用同一实现；verify 拒绝非规范
  S≥L、非曲线点与长度不符）。与第 4.5 节的差异：签名不放 signature.json，而是 manifest 的可选字段
  signature: {algorithm: "ed25519", public_key_id, public_key(hex 32 字节), signature(hex 64 字节)}；被签名的是去掉 signature
  字段后的 manifest 规范 JSON（sort_keys、ensure_ascii=False、separators (",", ":")，UTF-8）。manifest 含逐文件 sha256 与
  content_sha256，故签名覆盖整个包。check_manifest_signature(raw_manifest, registry) → SignatureCheck，status ∈ {unsigned,
  valid, invalid, untrusted_key}；字段格式错、算法不支持、验签失败都是 invalid（附原因）。公钥指纹 = sha256(公钥字节)，
  显示前 16 位分组；缺省 public_key_id = ed25519:<指纹前 16 位>。
- TOFU：validate_trusted_keys（注册表 trusted_keys 形状：public_key_id 字符集、64 位小写 hex 公钥、带时区的 confirmed_at_utc、
  id 不重复）；trust_decision(registry, signature) → TrustDecision：同 (id, 公钥) 已确认 → valid/trusted；未见过的 id →
  untrusted_key/confirm_new_key（需用户确认后写入）；已确认 id 但公钥不同 → untrusted_key/key_id_conflict（警示“换了密钥
  或冒用”，不自动替换，with_trusted_key 拒绝）。同一公钥换新 id 也按首次见到处理。
- content_library_rules：manifest 可选 signature（只做形状检查并保留）；validate_library_pack(zip, *, registry=None) 的
  PackReport.signature 为 SignatureCheck（无注册表时有效签名一律 untrusted_key），invalid 只报告不抛出；install_refusal(report)
  与 precheck_pack(..., signature=) 的 PackPrecheck.signature_error（列入 blocking_reasons 首位）拒绝无效签名；
  with_trusted_key(registry, public_key_id, public_key, *, now)；pack_signature(report, registry) 按最新注册表重判信任；
  source_signature_fields(report, registry) → 注册表 source 的 signature_status 及可选 public_key_id、key_fingerprint。

  记录，保持可读；invalid 不会被安装）；未带新键的旧注册表规范化结果逐字节不变。Q6 取建议值：不强制签名，
