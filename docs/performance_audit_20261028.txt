KanaMemory 0.22.10 性能检查（2026-10-28）

本轮基线：0.22.9 / 49d330e。优化首页、切题、手写草稿保存及共享例句分页，
不改变学习项、FSRS 参数、前置依赖、题型选择、已保存题目和复习日期。
无需数据库迁移；所有用户记录仍使用原有保存格式。

实测结果（本机 Windows Python 3.13 / SQLite，毫秒中位数）
1. 50,000 条当前会话历史、663 道未完成题、500 点笔迹：
   每笔持久保存 14.684 -> 3.142 ms；P95 15.285 -> 3.716 ms。
   已评分摘要缓存最多保存两个会话，本连接增删改、外部提交均会使其失效；
   事务内绕过缓存，避免回滚后的旧版本编号复用。仍然每笔 COMMIT，WAL/FULL。
   只有 663 道新题而没有答题历史时，保存约 3.3 ms，收益不明显。
2. 663 项已加入课程：补题检查 96.766 -> 2.724 ms。
   复用先前完整四年模拟的封存数据库副本（不是重新跑四年）：
   3365 项课程、5919 个能力状态，补题检查 275.722 -> 15.071 ms，
   SQL 数量 3368 -> 1；路线进度 73.111 -> 23.432 ms。
   只提前筛掉所有能力已有 pending 题的课程；原规划器继续决定题型和到期时间。
3. 4920 条真实随包共享例句、空合成学习库：
   准备当前页内容 208.904 -> 31.815 ms；重复获取例句服务 71.648 -> 0.005 ms。
   仍根据即时学习进度对整个结果集排序，只为当前页十条生成详细副本。
   四种查询全量结果哈希与旧版相同，拼接全部分页也与原结果逐条相同。
4. 默认学习路线首页不再计算随后立即被覆盖的旧版统计；单词剩余数仅构造尾题。

限制与后续候选
以上是局部 Python/SQLite 时间，不是 Pixel 9 Pro 帧率、端到端响应延时或真实用户数据。
首次完整例句服务仍需约 2.1–2.5 秒，主要是语料校验和复制；未通过跳过校验来提速。
有新评分后第一次草稿保存仍会重新计算摘要；首次解析大队列 JSON 的成本仍存在。
新数据加入时要继续保留缓存失效和回滚测试，不可仅按对象身份永久缓存。
