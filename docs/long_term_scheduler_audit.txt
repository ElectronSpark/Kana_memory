长期调度的独立合同与查询审计
日期：2026-10-27

范围
这是对实际本地业务 API 的独立验证，不是三年用户行为主模拟，也不证明真实人的学习效果。
长时间轴合同测试、查询规模基准和极端反复遗忘反例分别记录，不能混为同一个实验。

1. 已验证的时间与数据合同
tests/test_long_term_scheduler_contract.py 使用真实 StudyStore、LearningStore 与单独的 FSRS 实例。
1461 个模拟日内，三个内容的评分轨迹分别偏稳定、波动和反复 Again，包含定期三天短空档和30/45/90/120天连续空档。
每次实际提交后的完整 scheduler_state 与独立库重放结果逐字段相同；到期晚于提交，稳定性为正且有限，难度在有效范围内。
重复 finalize 不新增事件；周期导出导入后所有学习表保持不变；查询 current/counts 不产生学习写入。
另有400天停学检查：未完成输入仍恢复，曾经独立通过的前置不会因后来一次遗忘或暂停而重新封锁后续课。
新增性能索引在旧版 v1 数据库上按需创建，学习表无变化；批量 list_items 与逐条 get_item 的结构、顺序和计数一致。
相关合同及存储/依赖/探针/熟悉度/负荷回归共106项通过，见 environment/logs/long-term-contract-tests.txt。

2. 已确认并修复的长期性能退化
旧版 get_unit 每次按 unit_id 计数 learning_event，没有对应索引；list_items 又对每个内容的每个能力重复这一查询。
同一私有测试数据库包含300个内容、600个方向和12,000个通过公开评分 API 生成的事件，事件跨度1404天。
旧版0.22.0 list_items 三次查询中位耗时6705.60毫秒，优化后五次中位6.71毫秒。
旧查询计划为 SCAN learning_event；优化后为 unit_id 覆盖索引。返回对象与学习表校验和完全一致。
这是这一个桌面查询的约1000倍差异，不是整个 App 或手机帧率的性能承诺。
修复：增加按能力事件索引、成功证据的部分索引；list_items 用三条批量读取；没有前置依赖的内容直接返回，不扫描全历史成功证据。
完整复现：environment/benchmark_learning_history_reads.py。

3. 严格短步骤优先的边界
environment/probe_persistent_relearning.py 构造5个始终答错的已介绍项，每题20秒，每天3次、每次5分钟。
真实API执行30天、90次访问、1350次复习后，排队的新介绍一次也未展示。每个难项共271次评分（含初始种子）。
相同初态的对照在第4次开始能够回忆：20次复习后，当天第二次访问即出现新介绍。
因此，等待/队列不是损坏或重置；问题来自始终无法记住的少数项目能持续占据有限练习时段。
不能把该极端模型推广为一般学习者，也不能凭它直接宣称应无条件优先新增。
后续可考虑在反复失败后显式转回讲解或让用户调整目标；不能虚构成功、偷偷延长真实到期或删除旧题来制造进度。
此审计未修改该优先策略。是否需要产品调整须结合主模拟的异质表现结果。

4. 当前题型策略的解释
课程 probe_due 保持对独立输出的要求。支持文字输出的能力在已有评分之后，后续往往持续使用 TEXT 类型。
现有 test_learning_probe 明确覆盖这一策略。它不是卡片丢失，但长期题型分布应如实报告，不能把它描述为所有题型均匀轮换。
本轮未改变它，也未根据合成行为拟合个人 FSRS 参数。

5. 持续追加队列的真实快照读取
对40天 smoke 数据用 mode=ro 创建私有 SQLite 副本，重放相同 kana.ensure、learning.current、kana.peek API。
主热点是每次分发四次还原含历史题目的全量 Question 列表，而不是仅有一个已加入课程的 LearningStore。
保持当前调度代码完全相同，仅切换快照复制实现：1738题状态下30次分发中位72.354毫秒降至39.652毫秒，约减少45.2%。
新实现复用既有快照版本的容器复制计划，每次仍返回独立列表、Question、options及各层metadata可变容器；外部写入和回滚依赖原有版本失效。
两条重放结束后所有业务表 SHA256 完全相同：0914b235d8c8f5154643f8bedf58cd5e76683e816afb82f892374e041a02619a。
120项既有快照、追加、过滤、回滚、外部连接和词语键盘测试通过，另新增一项深层可变对象与旧答案格式隔离测试通过。
仍是 O(累计题单长度) 的全量公开列表；没有丢弃历史，也没有通过减少真实业务调用让仿真变快。此数字仅为桌面业务层，不代表Android端渲染耗时。
复现：environment/profile_long_term_dispatch.py，--legacy-copy仅在私有副本切换此前复制实现。

继续对真实20次评分及23次介绍的写入循环分析，发现每次尾部改变后仍会重建整个历史前缀的复制计划。
现按同位置原始快照的完整字典值比较，仅为变化的题重新构建私有模板；私有模板不先重复深拷贝，公开返回仍隔离。
相同WAL/FULL状态、相同轨迹的profile墙钟17.815降至12.400秒；get_session_questions累计9.072降至3.833秒；重建模板102519降至9908个。
评分结果、学习时刻、完整业务表校验和相同（2166c50a1a7a7c1a043b2a4216efab69ffe48b4d268380f8bec9a2a4443ab891）。
增加尾部排序、相同身份但前缀metadata/选项变化、跨连接更新、回滚后读取测试；122项专项回归通过。
独立审查另发现Python值相等会混同True/1及整数/浮点；复用前现检查全部JSON标量类型，保留浮点正负零，同连接与跨连接14项新增回归通过，总计136项通过。
并行运行造成计时噪声，以上是定位热点而非手机性能承诺。

6. 仿真持久化与备份边界
私有固定100题轨迹比较，WAL/FULL耗时86.07秒，WAL/OFF两次为63.56/59.33秒；完整业务表校验和三次相同。
最后一次FULL反向复测按要求中止，因此不是完整交叉实验。OFF只能用于可重建的合成数据库，不能把其耗时标成生产性能或崩溃恢复保证。
当前单份备份硬上限64MiB，包含所有历史表；导入前还需导出当前库作回滚，因此已有库超限也会阻止导入较小备份。
单会话快照同样受64MiB上限限制。真实1492次评分样本有1789题、1807412字节，平均1010字节/题；简单外推约6.64万题到达单会话上限，不能据此外推精确故障日期。
实际12000次课程评分基准的紧凑v8数据表约27.5MB；全长主模拟应记录实际导出是否失败，不隐藏失败或删历史使它通过。
长期应考虑按题保存快照，保留session与绝对索引，避免每次写整份历史；备份如改分块归档须另定格式、解包总量/单块上限及原子校验恢复，继续支持旧JSON。
本轮未改这些存储格式或备份限制。

7. 主线题单的按需读取及两万题规模基准
上述复制计划优化仍会在每次主线分发时创建全部历史Question。现保留默认公开API的list契约，新增显式lazy参数；主线控制器、服务与仿真适配器可选择按需读取。
按需视图持有当次快照，不延迟查SQLite；同一视图的索引和切片复用该视图的对象，不同返回视图的可变options/metadata隔离。旧视图在数据库更新、回滚或关闭后仍能读取其原始题目。
重排只处理未完尾部，历史前缀写回仍执行与原Question构造相同的字段顺序、旧答案别名与词语键盘标准化，因此完整业务表可逐行、逐字符串比较。
主线resume里的research标志检查改为等价原始metadata遍历，避免为一个布尔值还原全历史。页面反馈依然包含队列长度，只导出当前题目的维护答案，不导出其他排队答案。
单词练习入口及未显式选择lazy的外部调用保持旧list行为；不换session、不删除历史、不更改题序、调度、持久化格式或默认同步级别。

规模样本由environment/build_queue_scale_fixture.py通过公开start_session/save_session_progress/record_review生成，8个已选假名方向每天固定重复、附20个未完项。
这仅是长期累计历史的性能压力样本，不是符合到期节奏的用户仿真，不用于学习效果或保持率结论。种子阶段用OFF减少可重建数据写入成本，测量恢复WAL/FULL。
一万历史题样本：20次真实ensure/peek/评分循环从16.922秒降至12.287秒；单步中位608.819降至345.848毫秒。
两万历史题样本：同样20次循环从33.401秒降至19.826秒；单步中位1183.731降至618.501毫秒，P95从3169.135降至2098.904毫秒。
两万题再加入与feedback_wait_times原谓词完全相同的reviews_finalized_card部分索引后，同轨迹12.619秒，中位335.856毫秒，P95为1429.772毫秒。
三次两万题重放的完整业务表SHA256均为202605f9fce7bc1b0374891da2396f9b33a03138070b9eaa6fd67f192e43107a，评分轨迹一致。
旧数据库重新打开会透明补建索引；索引合同测试验证全部表值与反馈时间不变、EXPLAIN确实使用该索引。
时延是同一桌面并行其他任务时的业务层样本，含介绍及真实写入，不代表Android渲染；无新算法或删除API来获得加速。
10k按需路径profile中_adaptive_stages仍占约23.5%（40次重放约20万历史事件），feedback_wait_times原无索引占约13.6%。增量派生证据缓存的独立审计与测量另行记录。

最终集成回归覆盖99个文件、1957个唯一用例。单次完整运行1953通过、4个旧fixture失败，用时422.83秒。
3个生命周期用例把空页面标记误当成必须原样保留的输入；用HEAD原prepare方法也得到相同失败。现保留重启前快照严格相等、题序/游标不变及重复回调幂等，改为对比分发后的checkpoint。
另1个记录计数用例在同一时刻连续答同内容两种能力，违反已有60秒反馈曝光间隔；仅将测试时钟推进间隔加1秒。相关submit/finalize/effective_question_due/曝光方法与HEAD的AST完全一致。
修改测试后连同真实草稿/优先级合同定向复跑40项全过，用时14.35秒。按JUnit节点标识合并为1957个唯一通过用例，不把复跑累加；没有重复整个批次，也没有修改生产逻辑来适应旧断言。

最后一次真实副本诊断发现，升阶会反复尝试为お/ヲ/ず/づ/ジ生成独立听写，但单题builder必因同音歧义返回空；已有unfinished方向的过滤本身正确。
现仅在ensure_kana_queue对kana_handwriting候选使用原有_eligible_kana谓词，每次调用只读一次候选目录；不跨调用缓存、不改变seed/RNG调用位置、正常题的生成顺序与选项、取消语义或任何学习记录。
同一只读备份100次真实评分及必要介绍/分发，WAL/FULL耗时128.828降至106.687秒（约17.2%），单步中位526.611降至422.468毫秒（约19.8%）。
完整100条评分/到期轨迹和全部业务表均相同，SHA256为23f4b9a258e85181816dde0becb266945d22b27a991d3e39a7cf8d1cdd7f12b6。
最后受影响回归96项全过（31.58秒），含5个预筛新合同及同期新增的1个仿真计数抽查合同；按JUnit节点去重累计1963项通过。不是将1957、40、96相加，也未在最后预筛后再跑整个大批次。

8. 本轮补查的外部材料（2026-10-27）
Settles & Meeder (ACL 2016), A Trainable Spaced Repetition Model for Language Learning：
https://aclanthology.org/P16-1174/
https://github.com/duolingo/halflife-regression
原始研究利用语言学习数据拟合记忆半衰期，提醒我们区分“模型假设”和“真实观察”。
本轮仅借鉴独立遗忘过程的测试思想；没有使用论文数据拟合本 App 的用户，也不把合成正确率说成实测保持率。

Anki 官方手册 Leeches：
https://github.com/ankitects/anki/blob/main/docs-site/manual/leeches.mdx
官方将反复遗忘、占用大量复习时间的项目单独标记，并允许调整处理方式，建议检查材料是否太复杂或尚未理解。
这是现成产品策略的参考，不是“连续错几次必须暂停”的科学定律。本轮极端反复遗忘探针不据此自动暂停用户内容。

FSRS 维护者的教程：
https://github.com/open-spaced-repetition/fsrs4anki/blob/main/docs/tutorial.md
说明长时间中断后应如实回答，不能为清空积压把旧卡当作新卡或伪造学习记录。
本轮对长空档前后数据库逐表比较，并在恢复后继续使用原卡片、实际答题时刻和已存到期时间。

9. 未集成的提交后快照缓存实验
environment/experiment_snapshot_write_cache.py仅用于私有进程monkeypatch，不被应用导入，也未修改生产写入方式。
实验在既有SQL更新成功后记录连接data_version与TEMP revision，commit成功且token仍相同时才发布私有JSON形状快照；rollback或随后未知/外部写继续按原机制失效。
为防止公开Question的metadata污染缓存，只有原私有缓存中已知对象可共享，新容器独立复制，tuple正规化为JSON列表，保留bool/int/float差异。
固定5730条评分的真实仿真副本，100次实际ensure/peek/评分及必要介绍：WAL/FULL基线103.977秒，实验84.024秒（1.24倍），单评分步中位397.267降至336.155毫秒。
两次完整评分/到期轨迹与全部业务表完全相同，SHA256仍为23f4b9a258e85181816dde0becb266945d22b27a991d3e39a7cf8d1cdd7f12b6。
大JSON解码输入从约1.957GB降至134MB，但安全冻结新容器仍耗8.439秒；293次候选写入均于commit后发布。
该计时有主模拟并发，基线阶段另有短时合同测试与只读副本profiling，不能据此承诺稳定19%加速。收益未达到本轮重新改生产/重包所需的明显幅度，保留为后续优化证据，不集成。
7个实验边界合同和47个已有按需读取/追加/缓存合同通过；这54项属于实验验证，不叠加到正式集成回归的1963唯一数。
最新真实仿真只读副本为2027-11-27、616课程、1315待做课程题、7281次假名评分。10次热读中位：learning.current35.85ms，learning.counts210.21ms，kana.ensure34.31ms，kana.peek82.65ms，完整dispatch152.29ms，学习路线overview41.95ms。
课程current确随待初学内容增长，但当时profile主要仍是active题目复制与全历史恢复检查；该profile按每次验证counts运行，不等同于已采用抽样额外断言的主仿真耗时。


实验依赖边界：主模拟simulate_long_term_learning.py及long_term_kana_lane.py未导入orjson、静态语料实验cache或snapshot发布实验。主模拟使用准备环境中的fsrs等既有依赖；分析脚本不需额外加速库。绘图单独使用environment/requirements-long-term-report.txt中的matplotlib==3.11.2，不能加入Android requires。
只有environment/probe_long_term_harness.py显式--mode fast-load分支延迟导入orjson；默认baseline、static-content探针调用的baseline和主模拟都不需要它。此机实验版本为orjson==3.13.0。若另机要复现实验，应在独立研究虚拟环境显式安装该版本，并以--mode fast-load选择它；没有该包时仅该可选模式无法运行。
静态语料cache、snapshot发布cache及其benchmark使用标准库和既有应用依赖。snapshot实验测试额外使用已有pytest；不需要OpenAI密钥或网络。
所有这些基准必须以.test_runs中的合成数据库只读备份作为source，不能换成真实手机学习库。基准的精确前后对照依赖同一份master；合成DB不随源码分发，跨机器应先运行同版本主模拟或规模fixture生成输入，不能将新生成的UUID视为与旧证据的全表hash天然相同。
app/pyproject.toml仅声明fsrs与平台Toga依赖；当前0.22.1 APK外层及三个Chaquopy requirements归档均无orjson成员。environment/long_term_resume_notes.txt亦已明确主运行不使用实验codec/cache。
